# Fork conversation: frontend contract

A fork creates a new conversation (the **child**) that contains a copy of an existing conversation
(the **source**) up to and including one completed assistant reply. After that, the two are
independent. A message sent in either one never appears in the other, and editing or deleting a
message in one does not change the other.

There is one new endpoint and no new streaming protocol. The child is an ordinary conversation, so
use your existing message list, chat and streaming code for it.

## 1. Endpoint

```
POST /conversations/{sourceConversationId}/fork
```

| Client | Path |
| --- | --- |
| Direct to the API server | `/conversations/{id}/fork` |
| Through the local sidecar | `/conversations/{id}/fork` or `/api/conversations/{id}/fork` |
| AI SDK clients | Same path as above. There is **no** `/ai/conversations/{id}/fork`. |

Authentication is the same as for every other conversation route. Without a session the server
answers `401`, and the sidecar answers `401` or `403` without forwarding the request.

### Request body

```json
{
  "messageId": "6f1c9a2e-0d4b-4a51-9f7e-2b8c3d4e5f60",
  "requestId": "a3e9b1c4-7d2f-4e8a-b6c5-1f0e9d8c7b6a",
  "title": "Try the other approach"
}
```

| Field | Type | Required | Rules |
| --- | --- | --- | --- |
| `messageId` | UUID string | yes | The assistant reply to fork at. It is copied, along with every message before it. |
| `requestId` | UUID string | yes | Generated by the client, one per user action. See section 3. |
| `title` | string | no | 1 to 255 characters. If you leave it out, the title is `"<source title> (fork)"`, with the source title cut to 248 characters. |

### Success response

`201 Created` for a new child, `200 OK` when the same `requestId` is sent again. Both return the
same body shape, and a repeated request returns the same child.

```json
{
  "success": true,
  "message": "Conversation forked successfully",
  "data": {
    "id": "0b7e4d2a-5c1f-4e3b-9a8d-6f2e1c0b9a87",
    "createdAt": "2026-10-13T08:15:02.114Z",
    "updatedAt": "2026-10-13T08:15:02.114Z",
    "deletedAt": null,
    "ownerId": "…",
    "title": "Try the other approach",
    "personaPrompt": null,
    "planningModeEnabled": false,
    "planLifecycle": null,
    "projectId": null,
    "forkedFromConversationId": "c1d2e3f4-…",
    "forkedFromMessageId": "6f1c9a2e-…",
    "forkedThroughSequence": 4
  }
}
```

On a repeated request, `message` reads `"Conversation fork replayed"`. Use the status code (`201` or
`200`) to tell the two cases apart, not the `message` text.

### New fields on every conversation

Every conversation returned by any conversation route (`GET /conversations`,
`GET /conversations/{id}`, `/ai/conversations…`) now has these three fields. All three are `null`
on a conversation that is not a fork.

| Field | Type | Meaning |
| --- | --- | --- |
| `forkedFromConversationId` | UUID or `null` | The source conversation |
| `forkedFromMessageId` | UUID or `null` | The source reply the fork was taken at |
| `forkedThroughSequence` | integer or `null` | The last source message sequence copied (inclusive) |

**To tell whether a conversation is a fork, check `forkedThroughSequence !== null`.** Deleting a
conversation is a soft delete, so the two ID fields can still be set after the source has been
deleted. A request to that ID then returns `404`.

## 2. Errors

Every error uses the standard envelope:

```json
{ "success": false, "code": "FORK_POINT_NOT_COMPLETED", "message": "Only a completed assistant reply can be forked" }
```

Base your logic on `code`. The `message` text is for display and may change.

| HTTP | `code` | Cause | What the UI should do | Keep `requestId`? |
| --- | --- | --- | --- | --- |
| 404 | `CONVERSATION_NOT_FOUND` | Source is missing or deleted | Show an error and refresh the conversation list | no |
| 403 | `CONVERSATION_ACCESS_DENIED` | Source belongs to another user | Show an error | no |
| 404 | `FORK_MESSAGE_NOT_FOUND` | Message is missing, deleted, or not in this conversation | Reload the messages | no |
| 409 | `FORK_POINT_NOT_COMPLETED` | A user message, an empty placeholder, or an unfinished or paused reply | Say the reply can't be forked and hide the control | no |
| 409 | `conversation_turn_conflict` | The source has a turn running, or it was busy for longer than the lock wait | Say "busy, try again" and let the user retry | **yes** |
| 409 | `FORK_REQUEST_CONFLICT` | This `requestId` was already used for a different message or title | Generate a new `requestId` and retry once | no, generate a new one |
| 410 | `FORK_RESULT_DELETED` | The child created by this `requestId` has been deleted | Generate a new `requestId` if the user forks again | no, generate a new one |
| 409 | `FORK_DOCUMENT_CONTEXT_UNSUPPORTED` | The source has uploaded documents, which can't be forked yet | Explain the limitation and disable the control for this conversation | no |
| 413 | `FORK_HISTORY_TOO_LARGE` | More than 5,000 messages or 32 MiB of history, server defaults | Explain the limitation | no |
| 422 | `invalid_input` | Bad body, for example a non-UUID or a title that is empty or too long. `error` maps each field to its messages | Fix the client | no |
| 401 | | Not signed in | Your usual sign-in flow | |
| 5xx or network | | Transient failure | Let the user retry | **yes** |

`conversation_turn_conflict` is the same lowercase code the message routes already use. It can take
up to the server's lock wait (30 s by default) to arrive.

## 3. Request ID rules

The `requestId` makes a retry safe: sending the same ID again returns the same child instead of
creating a second fork.

1. Generate one `requestId` per user action, meaning one per (source, message) click, not one per
   HTTP attempt.
2. Keep it across retries after a network error, a 5xx, or `409 conversation_turn_conflict`.
3. Disable the fork control while a request is in flight, so a double-click can't send two
   requests.
4. Discard it after a success, `FORK_REQUEST_CONFLICT` or `FORK_RESULT_DELETED`. The next click
   generates a new one.
5. A new `requestId` always creates a new child. Forking the same reply twice on purpose is allowed.

```ts
const key = `${sourceId}:${messageId}`;
const attempt = attempts.get(key) ?? { requestId: crypto.randomUUID(), pending: false };
if (attempt.pending) return;            // already in flight
attempt.pending = true; attempts.set(key, attempt);
try {
  const res = await post(`/conversations/${sourceId}/fork`, { messageId, requestId: attempt.requestId });
  attempts.delete(key);                 // 200 or 201
  openChild(res.data);
} catch (err) {
  if (["FORK_RESULT_DELETED", "FORK_REQUEST_CONFLICT"].includes(err.code)) attempts.delete(key);
  else attempt.pending = false;         // retry later with the same requestId
  showError(err);
}
```

## 4. Where to show the fork control

Show "Fork conversation" only next to an assistant message that meets **all** of these conditions:

- it has been saved, so it has an `id`; text still streaming has no ID yet;
- it is an assistant row (`sender === 2` on canonical routes, `role === "assistant"` for AI SDK);
- its content is not empty;
- its metadata does not have `paused: true`;
- its metadata does not have `fork_cutoff_eligible: false`.

The server makes the final decision. A reply that passes these checks can still return
`409 FORK_POINT_NOT_COMPLETED`, for example a reply that was continued and is unfinished, or one
that was paused and shown from a stale cache.

A message can be forked while a later turn in the same conversation is paused waiting for
approval. Only the paused reply itself is ineligible.

## 5. After a successful fork

1. Insert `data` at the top of your conversation list.
2. Make `data.id` the selected conversation.
3. Load the child's messages from the server: `GET /conversations/{id}/messages` (canonical) or
   `GET /ai/conversations/{id}/messages` (AI SDK). **Do not build the child's history by slicing
   the source messages you already hold.** Your copy may be paginated, and the server changes
   the copied rows (see section 6).
4. Send all further chat, stop and continue requests to the child's ID. Use the same endpoints and
   stream format as for any other conversation.
5. Don't carry source-only UI state into the child. Clear pending approval or interrupt prompts,
   mounted live widgets and their subscriptions, composer attachments, and any message cache
   keyed by the source.
6. Don't send a stop or cancel to the source as part of forking. The server refuses to fork while
   a source turn is running, so a stop could only affect a paused source turn.
7. If you keep a generation snapshot (the `run_start`, `generation_status` and
   `continuation_available` events) so the user can resume a paused source turn later, show its
   Continue and Stop buttons, and send commands from it, **only** while the selected conversation
   matches the snapshot's `conversation_id`. Every lifecycle event carries `conversation_id`.
   Without this check, a paused turn's Continue button follows the user into other conversations.
   The same applies to ordinary conversation switching, not only forks.

## 6. Copied messages are read-only history

Each copied message is a new row with a new `id`. The original `createdAt` and sequence are kept,
so the copied history sorts correctly, and sequence numbers can have gaps. The copy's metadata is
cleaned up:

| Metadata | In copied rows |
| --- | --- |
| `fork_history` | **Always `true`.** Marks the row as copied history. |
| `fork_cutoff_eligible` | `true` or `false`: whether the server considered this reply a valid fork point in the source. Use it in section 4. |
| Text, model/provider attribution, citations, reasoning summaries, canvas content, static rich items | Kept |
| Chat images and selected web images | Kept if the user still owns them. Otherwise dropped (see below) |
| `reply_to_user_message_id` | Re-pointed to the copied user message |
| Interrupt or approval payloads, continuation and generation IDs, checkpoint IDs, pending tool calls, task-execution controls | Removed |
| Live widgets and other interactive rich items | Removed. The widget's position in the text becomes a plain text label |
| Feedback (thumbs up/down) and usage records | Not copied |

On any row with `fork_history === true`, **render no interactive controls**: no Approve or Reject,
no Continue, no "run next task", no live-widget or `mcp_app` iframe mount, and no re-run. Removing
the payloads already makes these unusable. The flag lets the UI hide them consistently.

Where the metadata is in each response:

| Route | Metadata field | Example |
| --- | --- | --- |
| `GET /conversations/{id}/messages` | `messageMetadata` (inner keys stay snake_case) | `msg.messageMetadata.fork_history` |
| `GET /ai/conversations/{id}/messages` | `metadata` (the same object) | `msg.metadata.fork_history` |

Images the user no longer owns when the fork is made are dropped from the copied metadata: chat
images, and web images that were never selected. The image's `<!--rich:...-->` marker stays in the
text and is listed in `rich_reference_warnings`. Render it as an unavailable-image block, the same
way you render any other missing rich reference. The text around it stays.

## 7. Lineage label

- If the conversation is a fork (`forkedThroughSequence !== null`) and `forkedFromConversationId`
  is in the user's conversation list, show **"Forked from <source title>"** as a link to the
  source.
- Otherwise, show the plain label **"Forked from a deleted conversation"**. This covers an ID
  that is `null` or not in the list. Don't create a link just because the ID is present: it may
  point to a deleted conversation.
- A fork whose source has been deleted keeps working normally.

## 8. What the child inherits

| Inherited from the source | Not inherited |
| --- | --- |
| Persona prompt, planning-mode setting, `projectId`, attached custom agents (as they are at fork time) | Task plans (`planLifecycle` is `null` and the child has no plans) |
| Copied messages, including canvas content as of the fork point | Paused or running turns, approvals, live widgets |
| | Uploaded documents (not supported yet; see `FORK_DOCUMENT_CONTEXT_UNSUPPORTED`) |

Project instructions, account memory, provider settings and custom-agent definitions are shared and
current. They are not copies taken at fork time.

## 9. Timing

- **The fork request** takes about 0.1 s for 100 messages and about 1 s at the 5,000-message
  limit, measured on a single local machine. Show a pending state on the control.
- **The first message sent in a child with a long history** may wait up to 15 s (server default)
  while the server summarizes the copied history. The stream sends `run_start` and
  `user_message_created` immediately, then nothing until the answer starts. Keep the "thinking"
  indicator and don't treat this gap as a failure. Later messages don't wait. If preparation fails
  or times out, the turn still answers normally, using the recent history only.

## 10. Checklist

- [ ] One `requestId` per action, kept across retries and discarded per section 3
- [ ] Control disabled while in flight, and shown only on eligible rows (section 4)
- [ ] `201` and `200` both open the child; errors are handled by `code` (section 2)
- [ ] Child messages loaded from the server, never sliced from the source
- [ ] No source approval, widget or attachment state in the child; the snapshot is scoped to its
      conversation
- [ ] No interactive controls on rows with `fork_history: true`
- [ ] Lineage label links only when the source is in the conversation list
- [ ] The pause before a long child's first answer is handled as normal
